# Decisions (defaults chosen where the brief left room)

1. **Auth is custom, not Auth.js cookie sessions.** The requirement "several users in several windows on one computer" needs per-window sessions; cookies are shared by all windows of a browser profile. Credentials + argon2 (pure-JS `@noble`, no native build) with bearer tokens kept in `sessionStorage` per window, `X-Petra-Window` / `X-Petra-Terminal` headers, hashed session rows server-side, lockout, idle lock, PIN switching. SSE authenticates with a short-lived `?token=`.
2. **Pages are client-rendered** (the session token lives in the browser), the API is server-side. Next standalone output is used as the shipped server.
3. **One catch-all API route + route table** (`route(method, path, {auth, perm, module, allowReadOnly})`) so permissions, licence/read-only gating, validation (zod), audit and the {ok,data}/{ok:false,error} envelope are enforced in one place; OpenAPI for the POS API is generated from it.
4. **SQLite via Node's built-in `node:sqlite`** behind a Prisma driver adapter (single connection + mutex, WAL, FK on, busy timeout) — avoids native modules (better-sqlite3) that complicate Electron/Windows builds. PostgreSQL uses a generated schema + migrations embedded in code and a runtime migrator with a pre-migration backup. **Requires Node ≥ 22.13** (Electron ≥ 38 bundles it).
5. **Overbooking prevention:** all inventory writes run in a transaction under an in-process mutex plus a PostgreSQL advisory lock; availability is recomputed inside the lock per room type per night (half-open date ranges).
6. **Money = integer poisha everywhere.** Tax: service charge 10% on net, VAT 15% on net + SC (compound), inclusive pricing back-calculates. Rounding per line, residue to the last tax.
7. **Idempotency:** night-audit room charges (`room:<stay>:<date>`) and POS postings (`pos:<OUTLET>:<check>`) use unique `sourceRef`s.
8. **Realtime = SSE** with topic invalidation of TanStack Query caches; PostgreSQL LISTEN/NOTIFY fans out in multi-instance cloud mode.
9. **Desktop shell in plain CommonJS (no TypeScript build step)** to keep the Electron main process tiny and auditable; it contains no business logic. Server runs as a child process using Electron's own Node (`ELECTRON_RUN_AS_NODE`). Windows Service uses WinSW (bundled by `node-windows`), firewall rule limited to private/domain profiles.
10. **Data location** `%ProgramData%\PetraPMS` (shared by the app and the service); the installer grants Users modify rights. Uninstall keeps data.
11. **Update safety:** the server takes a *pre-migration backup* the first time a new version starts; updates come only from a feed URL the customer/vendor configures (no telemetry, no phoning home).
12. **Licensing:** Ed25519-signed `PETRA1.<payload>.<sig>` keys verified offline; fingerprint-bound or floating; 14-day trial then read-only (HTTP 423 for writes); clock-rollback detection via a monotonic high-water mark; private key only in `tools/license-keygen` (git-ignored, excluded from installers).
13. **i18n:** next-intl with in-code message catalogs (EN/BN, parity enforced by a test); Bangla digits and lakh grouping are per-user formatting options, not translations. Avoid ASCII apostrophes in strings (ICU escape).
14. **Fonts bundled** (JetBrains Mono + Noto Sans Bengali, OFL) for UI and PDFs — no CDN.
15. **Mushak-style invoice** is a layout option modelled on common practice, not a certified NBR format.
16. **Notification providers** (SMS/email) are generic HTTP templates because Bangladeshi gateways differ; secrets stay server-side and are never returned to the browser or logged.
17. **Scope notes:** no channel-manager/OTA sync, no payment-gateway integration, no door-lock integration in v1 (extension points: POS API, notification templates).
18. **Licence key pair in source archives is for development.** Generate your own with `pnpm keygen init --write-app`; archives handed out for review exclude `tools/license-keygen/keys`.

### v1.0.1 — CI/CD hardening and Windows-sell-readiness (`ci/windows-hardening`)
19. **Reserved Windows device names fixed in `validateUserFolder`.** The admin-chosen backup/export folder is now checked for `CON`/`NUL`/`COM1-9`/`LPT1-9` segments and trailing dot/space, turning a raw Windows `fs` error into a friendly `BAD_FOLDER` message. Pure function `windowsNameProblem()` is exported so the check is unit-tested on any OS, and applied in `validateUserFolder` only on `win32` (these names are ordinary on Linux/macOS).
20. **CI artifact traceability:** `scripts/dist-win.mjs --test` now accepts `PETRA_TEST_BUILD_ID` (short commit SHA, set only in CI) and appends it to the test-installer file name, so repeated CI runs never overwrite each other's artifact and a failure can be traced to the exact commit. Local `pnpm build:win:test` is unaffected (no env var set, same file name as before).
21. **Installer smoke test runs against the actually-installed files**, not just the staged bundle: it drives the real NSIS silent installer (`/S /D=`), then starts the bundled server through `PetraPMS.exe` with `ELECTRON_RUN_AS_NODE=1` pointed at the installed `resources\app.asar\src\server-launcher.cjs` — the same code path WinSW uses for the Windows Service — using a scratch `PETRA_DATA_DIR` per check so repeated rows (upgrade/uninstall/reinstall) in one CI run don't interfere with each other. Only the uninstall/reinstall row uses the real `%ProgramData%\PetraPMS`, because that is what row #11/#12 of `docs/WINDOWS-VALIDATION.md` is actually about.
22. **Upgrade-test honesty:** there is no previous release artifact to upgrade from yet. The smoke test looks for one (env `PETRA_PREV_INSTALLER`, populated by a best-effort CI step that downloads the last successful run's artifact) and prints an explicit `SKIPPED: no previous build` row rather than a silent or faked pass when none is found.
23. **Server-mode Windows Service install/start/stop/remove runs in its own CI job, named and labelled "best-effort"**, with `continue-on-error: true` confined to that job only — never hidden inside the main smoke test, so a real regression there cannot silently go green.
24. **Release pipeline never auto-publishes.** `release-windows.yml` always creates a **draft** GitHub Release (`gh release create --draft`); a human reviews and publishes it after testing on a clean VM.
25. **Bug found by running `pnpm test` on Windows for the first time (CI iteration 1):** `validateUserFolder`/`validateDataDir` silently accepted a drive-relative path like `/etc` on win32 (`path.isAbsolute` treats it as absolute; it then resolves against whatever the current drive happens to be). Fixed by requiring a spelled-out drive letter or UNC share on win32, matching the example already shown to the admin.
26. **The one `ci.yml` e2e failure (CI iteration 2) was investigated, not just rerun.** This session's network policy blocks the blob-storage URL `gh run view --log` needs (confirmed: `results-receiver.actions.githubusercontent.com` is denied by organization egress policy, not a transient error), and the failed run produced no `test-results/` artifact at all — meaning it failed in `scripts/e2e.mjs`'s own server-readiness wait, before Playwright ever started (a Playwright test failure would still leave trace files behind; an empty artifact means it never got that far). That pinpointed the failure to one of two places: the server process dying on start, or it simply not answering in time. Locally (rebuilding and running the full suite against the pre-installed Chromium, including a deliberately forced `EADDRINUSE` to exercise the failure path) the suite passed every time and the forced-failure path correctly reported the real cause in under a second — so the previous code's blind 30-second wait-then-generic-error was itself the problem being fixed, not a reproduced app bug. `scripts/e2e.mjs` was rewritten to: (a) stop polling the instant the server process exits, instead of waiting out the rest of the timeout against a process that is already gone; (b) capture the server's stdout/stderr (previously only `stdio:"inherit"`, invisible to anything other than the raw job log) and report it as a GitHub Actions `::error::` annotation plus a `$GITHUB_STEP_SUMMARY` block, retrievable via the Checks API even when the raw log is not; (c) widen the readiness budget to a wall-clock 45s so a slow/cold runner gets the same real margin a fast one does. `playwright.config.ts` also gained the built-in `"github"` reporter in CI, so an actual failing *test* (as opposed to a server that never came up) is annotated with its own file/line/error natively. **Honest conclusion: the single occurrence was not reproducible locally and the raw CI log for it cannot be read from this session, so no single deterministic root cause can be claimed with certainty** — the fix is to make the next occurrence (if there is one) immediately diagnosable instead of a blind rerun, which is the most defensible response available given the policy-blocked logs.
